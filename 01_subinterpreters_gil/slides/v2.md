# What is a process?

<v-clicks>

- A process is a unit of execution with its own (separate) memory, file descriptors, execution state, etc.
- In Python, the process will have its own interpreter (and its own GIL).
- Creating new processes is a "heavy" operation — we need to copy everything the process has.
- In Python, starting a new process is done via either `fork` (Linux) or `fork + exec` (macOS & Windows).
- This is wrapped around in the `Process` object in `multiprocessing`.

</v-clicks>

# What is a thread?

<v-clicks>

- A thread is the smallest unit of execution.
- It shares memory and file descriptors with other threads.
- In Python, threads run in the same interpreter, with a shared GIL.
- Creating new threads is a lightweight operation.
- The `Thread` object from `threading` is the interface we use to work with threads in Python.

</v-clicks>

# The `concurrent.futures` module

<v-clicks>

- Provides a high-level interface for asynchronous execution of callables.
- `ThreadPoolExecutor` — pool of threads
- `ProcessPoolExecutor` — pool of processes
- Key methods:
  - `submit(fn, *args)` — schedule a single callable
  - `map(fn, iterable)` — map a callable over an iterable
- Returns `Future` objects; call `.result()` to retrieve the value.

</v-clicks>

# Example 00 — Baseline

```python {*} {maxHeight: '70%', lines: true}
import math
import sys
import time


NUMBERS = [
    112272535095293,
    112582705942171,
    112272535095293,
    115280095190773,
    115797848077099
] * 10


def is_prime(n):
    if n < 2:
        return False
    if n == 2:
        return True
    if n % 2 == 0:
        return False

    sqrt_n = int(math.floor(math.sqrt(n)))
    for i in range(3, sqrt_n + 1, 2):
        if n % i == 0:
            return False
    return True


if __name__ == "__main__":
    print(sys.version)
    start = time.time()
    for number in NUMBERS:
        is_prime(number)
    print(f"Single CPU took {time.time() - start:.2f} seconds")

```

# Example 01 — Multiple processes

```python {all|15|16|all} {maxHeight: '70%', lines: true}
import math
import sys
import time

from concurrent.futures import ProcessPoolExecutor

...

if __name__ == "__main__":
    print(sys.version)
    start = time.time()

    workers = int(sys.argv[1]) if len(sys.argv) > 1 else 4

    with ProcessPoolExecutor(max_workers=workers) as executor:
        executor.map(is_prime, NUMBERS)

    print(f"{workers} workers took {time.time() - start:.2f} seconds")
```

# What is a subinterpreter?

<v-clicks>

- A subinterpreter is **not** a new bytecode evaluation loop — that part is shared.
- What CPython allocates is a new `PyInterpreterState` — a C struct holding all independent state.
- Each subinterpreter has:
  - Its own **GIL** (since PEP 684 / Python 3.12)
  - Its own `sys.modules` (module registry)
  - Its own import state and builtins
  - Its own garbage collector state
  - Its own set of `PyThreadState` objects

</v-clicks>

# Sharing objects

<v-clicks>

- Subinterpreters **cannot** effectively share objects between themselves.
- Functions are **not shareable** when they have dependencies outside the new interpreter.
- `call()` requires "pure" functions — no closures over external state.

</v-clicks>

# `call_in_thread`

```python
from concurrent import interpreters


def sleepy_print():
    print("Hello from the subinterpreter!")
    import time

    time.sleep(2)


interpreter = interpreters.create()

t = interpreter.call_in_thread(sleepy_print)

print("Hello from the main interpreter!")

t.join()

interpreter.close()
```

# What is the GIL?

<v-clicks>

- The **Global Interpreter Lock** is a mutex that protects access to Python objects.
- It prevents multiple native threads from executing Python bytecodes simultaneously.
- Without the GIL, reference counting (CPython's memory management) would require locks on every object.
- The GIL is released during I/O operations, allowing some concurrency.
- It was introduced to simplify CPython's implementation and integration with C extensions.

</v-clicks>

# GIL-less Python

<v-clicks>

- Freethreaded Python removes the GIL entirely (PEP 703).
- Consequences to be aware of:
  - **Thread safety** — objects that were previously safe due to the GIL may no longer be.
  - **Immortalization** — some objects are made immortal to avoid reference-count contention.
  - **Iterators** — may not be thread-safe without explicit locking.
  - **Single-threaded performance** — slightly slower due to per-object locking overhead.

</v-clicks>

# Examples 00–03 with freethreaded Python

<v-clicks>

- The same four examples run under `cpython-3.14t` (freethreaded build).
- Key difference: threads are no longer limited by the GIL.
- `ThreadPoolExecutor` can now utilise multiple CPU cores.
- `InterpreterPoolExecutor` behaviour changes — each subinterpreter no longer has its own GIL.

```bash
$ uv python pin cpython-3.14.2+freethreaded
$ uv run python 00_baseline.py
$ uv run python 01_multiprocess.py 4
$ uv run python 02_multithread.py 4
$ uv run python 03_multiinterpreter.py 4
```

# Summary

<v-clicks>

- **Processes** — isolated, bypass the GIL, but heavyweight.
- **Threads** — lightweight, but blocked by the GIL (CPU-bound tasks don't scale).
- **Subinterpreters** — in-process isolation with a per-interpreter GIL; best of both worlds.
- **Freethreaded Python** — removes the GIL; threads scale for CPU-bound work, but ecosystem support is still catching up.

<br/>

## Choose subinterpreters today for CPU-bound parallelism; watch freethreaded Python closely as ecosystem support matures.

</v-clicks>
