# Parallel execution in Python

<v-clicks>

- We can achieve parallel execution with two methods - threads or processes
- Due to the **Global Interpreter Lock**, only **one** thread can execute Python bytecode.
- The GIL is released for I/O operations.
- To achieve parallel execution of code, we can use multiple processes.
- Each different process has it's own GIL

</v-clicks>

# Threads vs processes

<v-clicks>

| **Aspect**     | **Threads**                                                                       | **Processes**                                         |
| -------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Memory Sharing | Share the same memory space (lightweight)                                         | Separate memory spaces (isolated)                     |
| GIL Impact     | Limited by GIL                                                                    | Bypasses GIL                                          |
| Overhead       | Low creation/switching overhead                                                   | Higher creation/switching overhead                    |
| Communication  | Easy via shared variables/objects                                                 | Requires queues, pipes, or shared memory              |
| Best For       | I/O-bound tasks                                                                   | CPU-bound tasks                                       |
| Safety         | Risk of race conditions; needs locks/synchronization                              | Naturally isolated; safer for buggy code              |

</v-clicks>

# Subinterpreters

<v-clicks>

- CPython supports multiple interpreters.
- Each interpreter has its own runtime state. (Including a GIL)
- By default, the new interpreter is in the current thread.
- Support in CPython was present since Python2.2 (released 2001), but the high-level functionality and access was added in Python3.14.

</v-clicks>

# Usage

<v-clicks>

```python
from concurrent import interpreters


def foo(interpreter):
    print(f"Running in interpreter id: {interpreter.id}, from {interpreter.whence}")


# Call in current interpreter
foo(interpreters.get_current())


# Create a new subinterpreter and run foo in it
new_interpreter = interpreters.create()
new_interpreter.call(foo, new_interpreter)

```

# Subinterpreters + threads

<v-clicks>

- On their own, subinterpreters don't do much.
- But if we launch a new thread, and in that thread we switch to a new subinterpreter, we get a thread with a different GIL than the main one.
- The `Interpreter` object can allow this via the `call_in_thread` function

```python {14}
from concurrent import interpreters


def foo(interpreter):
    print(f"Running in interpreter id: {interpreter.id}, from {interpreter.whence}")


# Call in current interpreter
foo(interpreters.get_current())


# Create a new subinterpreter and run foo in it
new_interpreter = interpreters.create()
thread = new_interpreter.call_in_thread(foo, new_interpreter)
thread.join()
```

</v-clicks>

# Futures

<v-clicks>

- Futures were added in Python3.2.
- They model an interface for asynchronous execution of callables.
- Accessed via `Executor` class and its children.
- Can either call a single function once, via `submit()`
- Or can map a function over an iterable, via `map()`.
- `Future` objects are returned, from which we can get the result via `result()`.
- Not related to asyncio futures.

</v-clicks>

# Example

```python
def calculate_item(item: int) -> int:
    numerator = 99**item
    denominator = (99 * (item + 1)) ** 97
    return numerator // denominator


def calculate_single_thread(total_terms: int):
    jobs = list(range(total_terms))
    start = time.time()

    result = 0
    for job in jobs:
        result += calculate_item(job)

    end = time.time()

    total_time = end - start
    print(f"Single-threaded time for {total_terms} terms: {total_time:.2f} seconds")
```

```python {all|4|5|all}
def calculate_multi_thread(total_terms: int, amount_of_threads: int):
    jobs = list(range(total_terms))
    start = time.time()
    with concurrent.futures.ThreadPoolExecutor(max_workers=amount_of_threads) as executor:
        executor.map(calculate_item, jobs)

    end = time.time()
    total_time = end - start

    print(f"Multi-thread time for {total_terms} terms with {amount_of_threads} threads: {total_time:.2f} seconds")

```

```python {all|5|17|all}

def calculate_multi_process(total_terms: int, amount_of_processes: int):
    jobs = list(range(total_terms))
    start = time.time()
    with concurrent.futures.ProcessPoolExecutor(max_workers=amount_of_processes) as executor:
        executor.map(calculate_item, jobs)

    end = time.time()
    total_time = end - start

    print(f"Multi-process time for {total_terms} terms with {amount_of_processes} processes: {total_time:.2f} seconds")


def calculate_multi_interpreter(total_terms: int, amount_of_interpreters: int):
    jobs = list(range(total_terms))
    start = time.time()
    with concurrent.futures.InterpreterPoolExecutor(max_workers=amount_of_interpreters) as executor:
        executor.map(calculate_item, jobs)

    end = time.time()
    total_time = end - start

    print(
        f"Multi-interpreter time for {total_terms} terms with {amount_of_interpreters} subinterpreters: {total_time:.2f} seconds"
    )
```

# Threads vs processes vs subinterpreters

<v-clicks>


| Aspect         | Threads | Subinterpreters | Processes |
| -------------- | ------- | --------------- | --------- |
| Memory Sharing | Share the same memory space | Separate namespaces in same process | Separate memory spaces |
| GIL Impact     | Limited by (GIL) | Per-interpreter GIL | Bypasses GIL |
| Overhead       | Low creation/switching overhead | Very low (in-process, no OS involvement) | Higher creation/switching overhead |
| Communication  | Easy via shared variables/objects (with locks) | Channels for safe message passing | Requires queues, pipes, or shared memory |
| Best For       | I/O-bound tasks (e.g., network requests, file I/O) | CPU-bound tasks needing low overhead + isolation | CPU-bound tasks (e.g., computations, data processing) |
| Safety         | Risk of race conditions; needs locks/synchronization | Isolated namespaces; safer than threads, lighter than processes | Naturally isolated; safer for buggy code |

</v-clicks>

# Conclusion

<v-clicks>

- Subinterpreters (with threads) unlock real multithreading in Python.
  - Isolation, but communication is still easy.
  - Fast and multithreaded.
- Removing the GIL enables multithreading, without subinterpreters.
  - Requires a different build of Python.
  - Subinterpreters slow down without the GIL.
  - Other libraries may suffer

<br/>

## For now, <span class="s1">subinterpreters</span> are the way to go, but <span class="s1">multithreading</span> is no longer "broken" in Python.

</v-clicks>
